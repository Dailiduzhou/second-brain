## Kafka

Kafka 是分区日志与消费者组模型。它擅长把同步请求中的慢操作或不稳定操作拆为异步任务，但默认并不提供端到端精确一次语义；消费者应以幂等业务写入、正确的 offset 标记和可回放的失败处理来应对重复投递与重平衡。

## Riverqueue

Riverqueue 以 PostgreSQL 为任务存储和协调基础，适合希望把任务入队与业务数据写入放在同一数据库事务中的场景。与 Kafka 的长时间保留分区日志不同，选择它时应重点关注任务幂等、worker 并发度和数据库负载。

## NATS

NATS 面向低延迟的消息传递和服务间通信。引入 JetStream 等持久化能力后，还需要明确消费者确认策略、保留策略和重放边界；不要把核心可靠性假设建立在临时订阅之上。

## Redis stream

Redis Streams 将追加日志、消费者组和 pending entries list 建立在 Redis 之上，适合已经以 Redis 为主要基础设施的中小型异步场景。设计时要额外定义未确认消息的认领与回收流程，否则宕机消费者留下的 pending 消息会长期无人处理。

## 选择与检查清单

| 需求或风险 | 优先确认的问题 |
|---|---|
| 需要按同一实体保持顺序 | 消息 key 是否稳定映射到同一 partition / shard？ |
| 消费可能重复 | 业务操作是否幂等，是否有唯一键或去重记录？ |
| 失败后必须可追踪 | 是否记录原消息、失败原因、重试次数和最终去向？ |
| 需要延迟执行 | 延迟精度、积压时的行为和过期任务策略是什么？ |
| 服务重启或扩容 | context 取消、消费者退出和未确认消息如何恢复？ |

无论采用哪种中间件，都应把“生产成功”“消费者已收到”“业务已完成”“进度已确认”作为四个不同的状态观测。把它们混为一个“消息处理成功”指标，会让故障定位变得非常困难。
